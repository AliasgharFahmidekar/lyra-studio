# Lyra Studio architecture

## Product boundary

Lyra Studio is a standalone Windows application. It must not require edits to the Lyra Core plugin. The desktop app can evolve independently while the plugin continues its own roadmap.

The app must support the current early Lyra Core release and future widgets, templates, pages, recipes, and extension modules. Therefore, the desktop application must not contain a manually maintained list of widget names or hardcoded field layouts.

## Integration model

Use provider adapters:

- `IWidgetCatalogProvider`: discovers widget identifiers, labels, categories, versions, and control schemas.
- `IRecipeCatalogProvider`: discovers recipes and their format/version.
- `IPreviewProvider`: requests a temporary render from the actual WordPress + Elementor runtime and returns a preview URL/session.
- `IRecipeSerializer`: imports/exports provider-supported recipe formats without assuming all recipes are PHP or JSON.

The optional Preview Bridge is maintained separately in `integrations/lyra-studio-preview-bridge`. It does not modify or require Lyra Core. Do not add routes to Lyra Core as part of current Studio work.

## Dynamic control schema

The inspector is driven by typed metadata, not widget-specific WPF forms. The schema supports text, textarea, number, switch, select, color, URL/link, media, icon, nested group, repeater, responsive values, conditions, defaults, required state, labels, descriptions, and validation constraints. Unknown control kinds remain visible as unsupported metadata rather than silently disappearing.

## Preview integrity

The central preview surface is WebView2. It navigates to actual output generated by WordPress + Elementor with the target widget and its assets loaded. A local HTML mock must never be labelled as a real preview.

The preview transport creates a new WordPress Page in `draft` state and associates it with a UUID and owner. The client may update or delete only that session. Existing page IDs are never accepted as preview targets. Cleanup verifies exact post type, draft status, session UUID, and owner. If deletion cannot be verified, the session is left for expiry cleanup.

Elementor documents PHP `render()` as the frontend rendering path and JavaScript `content_template()` as the editor preview path. A desktop renderer that re-creates those templates is not equivalent to Elementor.

## WordPress capability discovery

The connection diagnostic sends read-only HEAD/GET requests to discover the REST root, preserve subdirectory paths, and report declared namespaces and route names. Route discovery does not prove that the current user is authorized or that a route supports preview.

## Credential and browser security

- WordPress Application Passwords are used only for REST Bridge requests.
- The WPF client protects the saved Application Password using Windows DPAPI `CurrentUser` scope. Only the encrypted Base64 value is stored in the connection profile.
- The Bridge client refuses to send credentials over HTTP.
- The returned preview URL must match the connected WordPress origin.
- WebView2 uses a normal WordPress browser login independently; Application Passwords do not authenticate the browser session.
- Never log credentials, Authorization headers, or preview URLs containing security tokens.

## Safety

- Connection diagnostics use only HEAD and GET.
- No publish, save-to-live-page, recipe rebuild, or plugin-file mutation.
- No existing page can be used as a preview target.
- Future mutating features require explicit confirmation and a separately reviewable operation.

## Current implementation

The desktop shell, provider-neutral manifest import, dynamic inspector, visual repeater editor, nested settings JSON, automated tests, WordPress REST diagnostics, optional Preview Bridge, DPAPI credential protection, and WPF create/update/close preview workflow are implemented. Live-site end-to-end validation and responsive viewport controls remain pending.
