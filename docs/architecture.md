# Lyra Studio architecture (initial)

## Product boundary

Lyra Studio is a standalone Windows application. It must not require edits to the Lyra Core plugin during the desktop-foundation phase. The desktop app can evolve independently while the plugin continues its own roadmap.

The app must support the current early Lyra Core release and future widgets, templates, pages, recipes, and extension modules. Therefore, the desktop application must not contain a manually maintained list of widget names or hardcoded field layouts.

## Integration model

Use provider adapters:

- `IWidgetCatalogProvider`: discovers widget identifiers, labels, categories, versions, and control schemas.
- `IRecipeCatalogProvider`: discovers recipes and their format/version.
- `IPreviewProvider`: requests a temporary render from the actual WordPress + Elementor runtime and returns a preview URL/session.
- `IRecipeSerializer`: imports/exports provider-supported recipe formats without assuming all recipes are PHP or JSON.

A future Lyra Core adapter may use an explicitly agreed read-only API, an admin-side bridge, or a local development integration. Do not assume endpoints exist until verified. Do not add routes to the plugin as part of this repository's initial foundation.

## Dynamic control schema

The inspector should be driven by typed metadata, not widget-specific WPF forms. Initial control kinds to support:

- text, textarea, number, switch, select, color, URL/link, media, icon
- group and nested group
- repeater with min/max and item schema
- responsive values (desktop/tablet/mobile)
- conditional visibility
- defaults, required state, labels, descriptions, and validation constraints

Unknown control kinds must remain visible as unsupported metadata rather than silently disappearing.

## Preview integrity

The central preview surface is WebView2. It must eventually navigate to an actual render generated by WordPress + Elementor with the target widget/recipe and its assets loaded. A local HTML mock must never be labelled as a real preview.

Responsive preview changes the preview viewport, not the underlying widget implementation. Preview sessions should be temporary and isolated from published pages.

## Safety

- Initial connection probe calls only `/wp-json/`.
- No publish, save-to-live-page, or plugin-file mutation.
- Keep connection data under the current user's LocalAppData.
- Future mutating features require explicit confirmation and a separate reviewable operation.

## Initial implementation

The first desktop commit provides the WPF shell, connection profile persistence, a WordPress REST connectivity probe, and placeholder states that clearly distinguish connectivity from provider capability. It does not claim widget discovery or rendering before a compatible provider exists.
