# Lyra Studio architecture

## Product boundary

Lyra Studio is a standalone Windows application. It must not require edits to the Lyra Core plugin during its desktop-foundation or preview-research phases. The desktop app can evolve independently while the plugin continues its own roadmap.

The app must support the current early Lyra Core release and future widgets, templates, pages, recipes, and extension modules. Therefore, the desktop application must not contain a manually maintained list of widget names or hardcoded field layouts.

## Integration model

Use provider adapters:

- `IWidgetCatalogProvider`: discovers widget identifiers, labels, categories, versions, and control schemas.
- `IRecipeCatalogProvider`: discovers recipes and their format/version.
- `IPreviewProvider`: requests a temporary render from the actual WordPress + Elementor runtime and returns a preview URL/session.
- `IRecipeSerializer`: imports/exports provider-supported recipe formats without assuming all recipes are PHP or JSON.

A future Lyra Core adapter may use an explicitly agreed read-only API, a separate optional Studio bridge, or a local editor integration. Do not assume endpoints exist until verified. Do not add routes to Lyra Core as part of the current Studio work.

## Dynamic control schema

The inspector is driven by typed metadata, not widget-specific WPF forms. The schema supports:

- text, textarea, number, switch, select, color, URL/link, media, icon
- group and nested group
- repeater with min/max and item schema
- responsive values (desktop/tablet/mobile)
- conditional visibility
- defaults, required state, labels, descriptions, and validation constraints

Unknown control kinds remain visible as unsupported metadata rather than silently disappearing.

## Preview integrity

The central preview surface is WebView2. It must navigate to actual output generated by WordPress + Elementor with the target widget/recipe and its assets loaded. A local HTML mock must never be labelled as a real preview.

Elementor documents PHP `render()` as the frontend rendering path and JavaScript `content_template()` as the editor preview path. A desktop renderer that re-creates those templates is not equivalent to Elementor. See [preview integration research](preview-integration-research.md).

Responsive preview changes the preview viewport, not the underlying widget implementation. Preview sessions must be temporary and isolated from published pages.

## WordPress capability discovery

The current connection diagnostic:

1. Sends a read-only HEAD request to the supplied site URL and looks for the WordPress REST API discovery Link header.
2. Falls back to the conventional `wp-json/` path while preserving a WordPress subdirectory path.
3. Reads the REST index with GET.
4. Reports the namespaces and route names that the index declares, including WordPress Pages, Elementor, and Lyra-related namespaces.

This is discovery only. A listed route does not prove the current user can call it, that it accepts Elementor document data, or that it provides a preview lifecycle.

## Safety

- Connection diagnostics use only HEAD and GET.
- No publish, save-to-live-page, recipe rebuild, or plugin-file mutation.
- Keep connection profiles under the current user's LocalAppData.
- Future preview writes must be limited to a Studio-created temporary draft with a unique session marker and expiry.
- Cleanup may delete only the exact draft created by that Studio session. If cleanup cannot be verified, leave it as a draft and show a warning.
- Future mutating features require explicit confirmation and a separately reviewable operation.

## Current implementation

The desktop shell, provider-neutral manifest import, dynamic inspector, visual repeater editor, nested settings JSON, automated tests, and WordPress REST index diagnostics are implemented. Real Elementor rendering and the temporary preview lifecycle remain pending until a safe, compatible transport has been selected and verified.
